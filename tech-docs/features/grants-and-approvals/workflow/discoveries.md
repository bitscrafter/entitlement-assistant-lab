| 1 | Spike K1 (pass) | In Wrangler's test harness, a Workflow instance (`step.waitForEvent` with a timeout) acts on a decision event, expires at its deadline ("Execution timed out after 2000ms" thrown into the step), and can be terminated; creating an instance whose id exists is refused with `instance.already_exists`. | Adopted: the approval process is a Workflow; a repeated start is treated as delivered. |
| 2 | Spike K2 (pass) | The harness triggers the Worker's `scheduled` handler (`/cdn-cgi/handler/scheduled`). | The sweeps run through the Worker in tests. |
| 3 | Judgment call | Revoking a grant is decided as its own action, `grant.revoke`, held through `grant.create` (like the case lifecycle keys through `case.open`). For the policy set's build check, `grant.revoke` is listed in the reference data as an Employee permission no role grants. | Owner approved (2026-10-27). |
| 4 | Judgment call (policy change) | `contact-is-authenticated` now also governs `grant.revoke`: D3 says a contact's request needs an authentication, and D12 makes revocation a contact's request when a contact is set. The policy set's version changes, so deploying re-registers it. | Owner approved (2026-10-27). |
| 5 | Judgment call | A contact with a hold holds no customer permission: the contact access step answers `access.contact-permission-not-held` (as a suspended principal may not act, AC-6). | Owner approved (2026-10-27). |
| 6 | New reason code (vocabulary) | A grant on a metered feature without a quota is refused with `entitlement.quota-required-on-metered-feature` (EN-4 says a metered grant adds quota; the spec did not name the refusal). | Owner approved (2026-10-27). |
| 7 | Judgment call | A refusal at confirmation leaves the request `AwaitingConfirmation`: once the reason is fixed (the contact authenticates, say), the same card can be confirmed. `Refused` is kept for refusals after approval (D8) and denials (D7). | Owner approved (2026-10-27). |
| 8 | Judgment call | Confirmation re-checks the request's own contact: if the case's contact changed since preparing, the request's contact counts as not authenticated. | Kept: what is confirmed is what was shown (SU-4). |
| 9 | Design | The decision point gains a System principal (`sys_approval_process`, `sys_grant_expiry`), whose permissions come from its assigned roles; the application finds each system account by its identity's name. | Needed for D8–D10's records and decisions. |
| 10 | Design | The dependency rule `subsystems-meet-through-use-cases` led to two Entitlement use cases in front of its model: `CheckGrantEligibility` (EN-4) and `CountGrantedTotals` (D5) for the decision point (renamed by the owner, discovery 33), `EntitlementDiffs` for Support. | Kept. |
| 11 | Test fix | The grants test helpers minted session tokens fixed to 2026-10-22, so a decision made after the clock moved to the 25th was unauthenticated (S26b case A answered 401 instead of 409). They now mint tokens valid at the harness clock's instant. | Fixed in the RED test's support code. |
| 12 | Test change | Case-lifecycle S33k pins the case agent's exact tool list; it now lists the three preparing tools too (none changes the case). | Updated. |
| 13 | Judgment call | The approval process expires an approval only on the Workflow's timeout ("timed out"); any other failure of the wait is retried, so a fault never expires an approval early. The sweep also expires approvals past their deadline, in case a process was lost. | Superseded by review R1-1 and R1-2: the matching was not enough. |
| 14 | Judgment call | `approval.expire` is held through `change-request.apply`, which the system role already has; no new permission. | Owner approved (2026-10-27). |
| 15 | Judgment call | The change request read (`GET …/change-requests/{id}`) is for the case's assignee and makes no new decision: it shows what preparing showed, with the status since. | Reversed by review R1-4. |
| 16 | Schema | `change_request` gains `preview_reason_codes`, so the card and the approvals panel show the preview's reasons after a reload (D2). The migration is not deployed yet. | Added to Support `004`. |
| 17 | Mutation checks | Killed: the contact permission ignored, D5 counting only the request, the self-approval decision skipped, the re-run at application skipped, the contact's authentication judged at application instead of at confirmation, the stale check skipped, EN-4's already-included rule ignored. The deadline is checked twice (the use case, and the conditional update in the same transaction): removing either alone survives, removing both is killed by S26b case A. | Kept both layers: the update is the race-proof one. |
| 18 | Vocabulary (for review) | New names: ports `TransactionalOutbox` (shared) and `ApprovalProcess` (application); adapters `PostgresTransactionalOutbox`, `WorkflowApprovalProcess`; use cases `CheckGrantEligibility`, `CountGrantedTotals`, `EntitlementDiffs`, `ChangeGrants`, `GetGrant`, `RecordGrantExpiries`, `AccountVersions`, `ApplyChangeRequest`, `PrepareChangeRequest`, `ConfirmChangeRequest`, `CancelChangeRequest`, `GetChangeRequest`, `ListPendingApprovals`, `DecideApproval`, `ApplyApprovedChange`, `ExpireApproval`; action keys `grant.revoke`, `change-request.prepare`, `change-request.confirm`, `change-request.cancel`, `approval.expire`; the Workflow class `ApprovalProcessWorkflow`. | Owner approved (2026-10-27). |
| 19 | Deployment note | `npm run policies:register` records `git rev-parse HEAD` as the set's revision, so registering before the feature is committed would record the wrong revision. | Commit before registering. |
| 20 | Review R1-1 (High, fixed) | An approval decided in time could be lost: if the decision reached the Workflow after its timer fired, the deadline wake found the approval `Approved`, did nothing, and the instance completed; the request stayed `AwaitingApproval` forever. Now a deadline wake applies an approved change, and the sweep applies any approval `Approved` whose request still awaits approval. The Workflow adapter also treats a failed `get` like any other delivery failure. | Fixed; tests R1-1 (two cases). |
| 21 | Review R1-2 (Medium, fixed) | Any error whose text contained "timed out" would expire an approval early. `ExpireApproval` now expires only once its deadline has come, so an early wake changes nothing. The Worker test moves the application's fixed clock to the deadline as the real timer fires. | Fixed; test R1-2. |
| 22 | Review R1-3 (Medium, fixed; worse than reported) | Closing a case while a supervisor decides its approval deadlocked (the race test reproduced it: 500). The cause was wider than the review's lock-order note: closing holds the case and the audit chain head, then locks requests; deciding held the request, then wanted the chain head. Every approval path now locks the case first, then the request, then the approval; records come last. | Fixed; race test R1-3, repeated. |
| 23 | Review R1-4 (Medium, fixed) | Reading a change request made no fresh decision: a CSR who lost the permission, or may no longer read an Enterprise subject, still read its diff. The read now passes the change's permission gate and decides `account.read`, recorded, refused as any read. | Fixed; test R1-4. |
| 24 | Review R1-5 (Medium, fixed; spec gap) | `approval.decide` is its own role, so an approver could see and decide approvals on accounts they may not read. The panel now lists only approvals on readable accounts, and deciding one on an unreadable account is a recorded `404`. D7 did not say; this follows AU-4 and AU-6. | Fixed; test R1-5. Owner approved (2026-10-27). |
| 25 | Review R1-6 (Low/Medium, fixed) | The sweep's stages now run independently (one failure no longer skips the outbox), and a message that failed 50 times is no longer redelivered: it stays, with its last error, for an operator. | Fixed. |
| 26 | Review R1-7a (Low, fixed) | D5 counted only the latest subscription's grants, so a new subscription restarted the 90-day count. Days are now counted over every grant of the account. | Fixed. |
| 27 | Review R1-7b (open question) | `grant-quota-up-to-100` checks each grant alone: two overlapping +100 seat grants of 14 days reach +200 with no approval. D5 counts days cumulatively; the spec does not say whether quota is cumulative too. | Owner chose cumulative (2026-10-27): `context.quota` is the grant's quota plus the feature's overlapping grants' (an extension's own grant not counted twice); D5 amended; the policy's description updated; test S21c case J2. |
| 28 | Review R1-8 (Low, fixed) | If the system identity was refused `change-request.apply`, the request stayed awaiting approval forever. It now ends `Refused` with the reason, recorded. | Fixed. |
| 29 | Review R2-1 (Medium, fixed) | R1-7a's fix read every grant of the account on every effective-entitlements computation, by a sequential scan, sometimes while holding the audit chain's lock. D5's days now read only the feature's grants still granting in the 90-day lookback, only when a grant change is decided (`CountGrantedTotals` reads them), with indexes on `subscription(account_id)` and `entitlement_grant(subscription_id, feature_key)`. | Fixed. |
| 30 | Review R2-2 (Low/Medium, fixed; judgment call) | Closing a case canceled a request whose approval was already `Approved` but not yet applied, voiding the supervisor's decision. Closing now leaves such a request to the approval process, which applies it after the case closes. D14 speaks of pending approvals only. | Fixed; test R2-2. Owner approved (2026-10-27). |
| 31 | Review R2-3 (Low/Medium, fixed) | If the system identity was refused `approval.expire`, the approval stayed `Pending` past its deadline forever, and each sweep retried the same ones. It now ends: the approval `Canceled`, the request `Refused` with the reason. | Fixed. |
| 32 | Review R2-4, R2-5, R2-6 (Low, fixed) | The approvals panel lists at most 50, in one query; a repeated Workflow start is recognized by the instance existing, not by an error's text; the account version lock is `FOR NO KEY UPDATE`. | Fixed. |
| 33 | Vocabulary (owner, 2026-10-27) | The grant rules are two kinds, so two use cases: `CheckGrantEligibility` (EN-4: whether a grant may exist; it refuses) and `CountGrantedTotals` (D5: days and quota granted, facts the policies judge; the limits live only in policies). `ChangeApplication` is `ApplyChangeRequest`, the shared last step of confirming and of the approval process, which decides nothing; the entitlement diff moved into `PrepareChangeRequest`. | Renamed. |
| 34 | Live check (2026-10-27, deployed) | Against the deployment, as Alex and Morgan: prepare and confirm 7 days (Allow, applied); 30 days (Conditional, 202, listed for Morgan, approved, applied by the real Workflow); seats +20 for 20 days denied by Morgan (Refused); an extension (applied); a revocation; the model then read the case's events back. The first run found one gap: after an extension the model revoked by the grant id it had read before, and the refusal ("not active") did not say where the grant went. A change on an extended grant now names its active successor (`f46dc3b`, test added); the second run passed all 13 checks (`5619c7ef`). | PASS. |
